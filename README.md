# 求职 / 申博进度追踪

两个独立的单文件追踪工具，分别服务秋招求职（`index.html`）和博士申请（`phd.html`）两条时间线。两者视觉风格一致、页面顶部互相有跳转链接，但数据、逻辑完全独立，互不影响——因为求职和申博的信息结构差异较大（前者是"公司→职位"的层级关系，后者是"导师↔项目"的多对多关系），硬塞进同一套数据模型只会让表单里堆满两边都用不上的字段。

## `index.html` · 秋招求职追踪

用来记录投递进度，按公司关注、具体职位、实际投递三个层级组织信息，方便回顾自己实际在关注哪些行业和岗位方向。

### 三层结构

一次求职决策通常要经历"知道公司→锁定职位→实际投递"这几个由模糊到明确的阶段，所以数据也拆成对应的三层：

- **🏢 公司关注**：只知道公司值得盯着，还没确定具体岗位。记公司名、行业、公告/官网链接、备注即可。公司卡片可以展开查看已经派生出的具体职位。
- **📌 待投递**：已经锁定的具体职位，尚未投递。每条记录标注：
  - 关注类型——**计划投递**（近期打算投）或 **长期关注**（感兴趣但暂不投，可选填原因，如能力/经验暂时不够、岗位尚未开放申请等）
  - 职位类型——全职/实习/应届生项目/科研/兼职/其他
  - 截止日期——支持标记**滚动招聘（Rolling Basis）**，即没有固定截止日期的岗位
  - 优先级、薪资、地点、可关联到已有的关注公司
- **📋 投递追踪**：已经投出的申请，看板或列表视图，按状态（已投递/已查看/面试中/已录用/已拒绝）流转，每条记录可以记录完整的流程时间轴（笔试、面试、Offer Call 等环节及日期）。

顶部统计栏显示总投递数、面试中、已录用、录用率。

数据存储在浏览器 `localStorage`（`jt4` 投递追踪 / `jt4_toApply` 待投递 / `jt4_companies` 公司关注），不上传到任何服务器，换浏览器或清缓存会丢失，建议定期用"导出"功能备份成 JSON 文件。

配套的 `api/extract.js` 是一个无状态的 Vercel Serverless Function，把粘贴的职位页面文字（或 URL）转发给 DeepSeek API，自动提取公司、职位、行业、职位类型、来源渠道，用于表单里的"自动填写"功能。需要在部署环境配置 `DEEPSEEK_API_KEY` 环境变量。

## `phd.html` · 博士申请追踪

用来记录套磁进度和网申项目进度，两者是多对多关系（一个导师可能关联多个网申项目，一个网申项目也可能关联多个联系过的导师），所以做成两个独立列表、互相关联，而不是像秋招那边那样做严格的层级结构：

- **🧑‍🏫 套磁记录**：导师姓名、所在院校、研究方向（自由填写，输入框会用浏览器原生的 datalist 自动检索你之前填过的方向做补全）、套磁进度（待发送→已发送→已回复→已约谈→成功/未成功）、沟通反馈时间轴（自由记录日期+内容，不设固定环节名称，因为套磁反馈内容因人而异）、可多选关联网申项目。
- **🎓 网申项目**：学校、项目/院系、申请批次、截止日期（同样支持标记**滚动招生**，即无固定截止日期）、网申状态（材料准备中→已提交→审核/面试中→已录取/Waitlist/未录取，Waitlist 单独列出是因为它和"未录取"是完全不同的状态）。卡片展开会反向显示关联的导师，不需要两头分别维护。

数据存储在 `localStorage` 的 `phd_professors` / `phd_applications`，与秋招追踪器的存储完全独立，互不影响。目前还没有做研究计划模板库（相似方向导师共用的研究计划模板管理），后续视需要再加。

## 技术实现

- 两个都是纯静态单文件（`index.html` / `phd.html`）：React 18 + Babel Standalone，均通过 CDN 引入，无需构建步骤，直接用浏览器打开即可运行，共享同一套视觉样式（配色、卡片、弹窗动效）。
- 两个页面顶部各有一个跳转链接互相导航，但不共享任何数据。

## 使用

直接用浏览器打开 `index.html`（秋招）或 `phd.html`（申博）即可使用，两边头部都有链接可以互相跳转。自动提取功能需要项目部署在支持 Serverless Function 的平台（如 Vercel）才能生效，本地直接打开文件时会自动降级为手动填写。数据的导入导出入口在 `index.html` 的"投递追踪"页顶部（`phd.html` 目前没有导入导出，数据全靠 localStorage 常驻）。
